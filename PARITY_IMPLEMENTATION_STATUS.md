## Use the new tools

Launch the project with `python3 desktop_app.py`, select a company, press F3 and choose **Company Tools**. Backups, valuation, payroll accounts, GST registrations, local IMS, XLSX import/export, SMTP delivery and capability requirements are available there. F11 loads and saves company feature choices.

To protect a company, open Company Management → Security. Create the first administrator using the masked form and enable **Require company login**. Store credentials securely; unsecured companies intentionally retain local owner mode. Credentials are stored in browser sessionStorage rather than shared localStorage.

## Group reporting and monthly GST book review

In **F3 → Company Tools → Consolidated company reports**, select members and enter a group name. Protected members can be authorised with the masked member-login form without changing the active company. Select debit/credit member ledgers, amount and reference to add a reporting elimination. Save the group or run a preview. Its before/after totals, trial balance and balanced elimination journal are rendered as tables; adjustments are never posted into source books. Over-elimination, wrong ledger sides, mixed currencies/financial years, unauthorised members and legacy multi-company files are rejected. Group definitions store no credentials.

In **GST books by registration and month**, select a month and registration, then review posted GST or download the review JSON. Main, additional and all registrations are separate scopes. Newly posted sales/purchase/POS vouchers preserve party GSTIN and item-rate/HSN snapshots. Old unsnapshotted vouchers are marked as using current masters. Cancelled/optional vouchers are omitted; unclassified credit/debit notes and foreign-currency documents are explicitly excluded. Warning tables identify missing details and mismatches. These book totals are not a GSTN schema, eligible ITC calculation or tax-payable determination.

## Access an existing native Tally company

The company chooser now detects native company folders instead of showing them as empty. Choose either their parent directory or the company folder itself. Select the native entry to inspect its format, detected name hint and file inventory. Metadata preview does **not** open financial books in the local accounting engine. Creating local books inside a native company folder is blocked.

After updating source files, fully stop the old Python backend before launching `start_tally.command` again. Browser refresh alone can load the new interface while the old backend remains in memory. This mismatch was confirmed in Safari: the live `/api/storage` response omitted `native_companies`, while a fresh process detected company `100124` directly. The chooser now identifies this outdated response explicitly and explains how to restart instead of reporting that the folder is empty. Catalogue requests bypass the browser cache. The running backend could not be restarted in this session because the execution sandbox blocks local server binding.

The **Connect to TallyPrime (read-only)** view can request actual data from a running TallyPrime engine without manual exports:

1. On the Windows computer that runs TallyPrime, load the original company and configure TallyPrime as Server/Both on its desired port (commonly 9000).
2. In TallyForge, enter `http://127.0.0.1:9000` if TallyPrime runs on the same computer. Otherwise enter the Windows computer's numeric private LAN IP and port, for example `http://192.168.1.10:9000`. The default localhost URL does not reach another computer or VM.
3. Choose **List loaded companies**, select the company, then **Read ledgers** or **Read vouchers**. A voucher date range is optional; without one, TallyPrime's current reporting period applies.

All bridge requests are fixed export requests. There are no import, alter or delete operations. Response sizes are bounded; redirects, public/metadata endpoints, and XML entity declarations are rejected. Raw Tally amount strings retain their formatting/signs and are never silently converted into local accounting entries. Paging re-requests the source and does not provide a transactionally frozen cross-page snapshot.

**Direct-reader progress:** an experimental `.1800` preview reads master-name fields, voucher search keys and linked transaction metadata without Windows or a running TallyPrime engine. It validates page checksums, declared chain lengths and bounded continuation links, retains byte provenance, and exposes search, pagination and reconstructed root-record details. The supplied company yielded 2,277 master-name roots, 131 voucher search-key candidates and 40,348 transaction headers with 80,696 validated metadata references. Numeric candidates retain exact raw bytes and signed/unsigned decimal strings; no currency scaling or date meaning is assigned. These are physical candidates, not active ledger/voucher totals. Inventory and live-connection controls are collapsed. See [docs/native-reader.md](docs/native-reader.md) for format observations, attribution, tests and limitations.

**Current limit:** no standalone financial decoder for `.1800`, `.900` or `.500` is implemented. Active-record selection, balances, amounts and allocations remain incomplete. Candidates are never imported as posted entries, and no financial amount or report is invented. This session did not have a running TallyPrime endpoint or reference exports, so no live financial reconciliation claim is made.

**Tally XML import into real books (2026-11-11, branch `feat/tally-xml-import`):** `engine/tally_xml_import.py` and the `import_tally_xml.py` command import Master/DayBook/Transactions XML exports into a new numbered TallyForge company, or re-sync the same company on later runs. Unlike the older `import_tally_xml` method in `accounting_db.py` (float arithmetic, keyword-guessed groups, auto-created suspense entries), it parses amounts as Decimal, rejects foreign-currency/formula amount strings, rejects ISDEEMEDPOSITIVE/sign disagreements and unbalanced vouchers instead of balancing them, requires every posted ledger to exist in the master export, keys records by Tally GUID and runs in one transaction. Source files are only read and hashed.

Verified on the supplied `100124` exports (independent Decimal figures from the XML vs. the resulting SQLite database and the app's own trial-balance report): 32/32 groups (7 created, flags/parents from XML), 1,980/1,981 ledgers, 79/79 Sales vouchers (49 April, 30 October 2026), 188 ledger allocations (the same count the native reader matched), 44 bill allocations, 104 inventory lines, every voucher Dr = Cr, all 15 posted ledgers' closing balances equal, trial balance <total withheld> Dr = Cr. A second run changes nothing (79 vouchers unchanged); SHA-256 of the three XML files is identical before and after. 11 new tests in `tests/test_tally_xml_import.py` also cover Payment/Receipt/Journal/Contra vouchers and opening balances using synthetic exports.

Not verified / known gaps from this source:
- **Opening balances:** none of the 1,981 ledgers carries `OPENINGBALANCE` in Master.xml. They are imported as 0 and flagged `opening_known=0` in `tally_import_record`; the trial balance therefore reflects only the exported vouchers, not real closing balances.
- **The two "currencies"** are one record (₹, same GUID) listed twice; one base currency is created.
- **Profit & Loss A/c** (primary-level, no group, no postings) is skipped because TallyForge ledgers require a group.
- **49 DayBook vouchers have no VOUCHERNUMBER** in the export and are stored with an empty number.
- **Stock items** are not in the master export; 24 placeholders (name + unit only, GST rate 0, no HSN) and 5 units are created from voucher lines. Stock positions are not meaningful.
- The import is CLI-only; it is not yet wired into the F3 Company Tools UI.

Regression run on Windows (Python 3.14, no pytest; browser and performance suites not run): accounting advanced/certification, enterprise capabilities, banking/payroll, company store, consolidation/GST books, ERPNext, inventory/manufacturing, monthly payroll, native TLV/voucher/Tally access, reliability, security audit/RBAC, statutory compliance/validation, TDL compatibility/laboratory/reference corpus and UI endpoints pass. **Live import from a running TallyPrime (2026-11-11, branch `feat/tally-live-import`):** `engine/tally_live.py` plus request builders and a hard read-only guard in `engine/tally_bridge.py` fetch company info, all masters, per-ledger opening/closing balances, a voucher census, per-month vouchers and Trial Balances (at the books-beginning date and at the last voucher date), feed them through the same Decimal/transactional/GUID-keyed importer, and compare the result with TallyPrime's own reports. `import_tally_xml.py --live URL --company NAME --capture-dir DIR --confirm-live` runs it; `--replay-dir DIR` re-runs a capture fully offline. `assert_read_only` refuses anything but `TALLYREQUEST=Export`, data objects, `ACTION` attributes, modifying collections and wildcard fetches. Requests are sequential and the first failure aborts without retry. 28 new tests use synthetic XML and a fake transport (they also assert that no non-Export request is ever sent).

**Incident — please read:** while probing the live server on 2026-11-11 I sent a Voucher collection request with wildcard fetches (`AllLedgerEntries.*`). TallyPrime stopped responding, grew to about 3 GB, then its process disappeared and restarted with no company loaded. Unsaved work in that TallyPrime session may have been lost. Wildcard fetches are now rejected by the bridge guard. Whether the explicitly named voucher methods in `VOUCHER_METHODS` are safe and return ledger entries on this server is **untested**.

What real TallyPrime responses showed (captured before the incident; kept outside the repository because they hold company data):
- The ledger collection reports `OpeningBalance` 0.00 for all 1,981 ledgers, so opening balances are known zeros (not missing), matching the file export. The books-beginning Trial Balance returns an empty envelope, consistent with all-zero openings.
- The Day Book *report* ignores the requested date range on this server (one voucher returned for any range), so it cannot be used for history; the Voucher *collection* honours dates. A census returned 22,343 live vouchers: Payment 16,152, Receipt 3,043, Sales 2,092, Purchase 615, Contra 262, Journal 165, Purchase Order 9, Stock Journal 5; none cancelled, optional or deleted. Only the 79 Sales vouchers have been imported so far; Payment, Receipt, Purchase, Contra, Journal and the inventory-only types are not yet imported, so no live Trial Balance equality has been demonstrated.
- Trial Balance XML shows debits as negative numbers, lists only some ledgers individually (42 ledger rows, 21 group rows) and prints a line break in a ledger name as `- `. On that real data the 42 ledger rows and 21 group rows equal TallyPrime's own ledger collection to the paisa, which validates the parser and sign convention. One pair of ledger names collapses to the same display name; they are compared as one row and the output says so.
- TallyPrime's Trial Balance balances only with a `Profit & Loss A/c` row of net debit <amount withheld> (the top-level groups alone differ by exactly that amount). The verifier does not absorb such a row; it compares it with the balance the vouchers give the P&L ledger. On the full run they are equal (vouchers post Dr <amount withheld> to `Profit & Loss A/c`).
- Group-less ledgers such as `Profit & Loss A/c` are imported into an explicit group, `Primary (ungrouped ledgers)`, rather than dropped or balanced by invention.

**One live month, verified (2026-11-11, after the user reopened the company):** a single guarded request for October 2026 (named fields, no wildcards) returned in 0.1 s, 184 KB, and TallyPrime stayed healthy. Compared with the file export `Transactions.xml` of the same 30 Sales vouchers: identical GUID set, 30/30 headers (date, number, type, cancelled, optional), 30/30 ledger-entry sets, 30/30 inventory lines (item, quantity, unit, rate, amount), 30/30 narrations and references, all balanced. This exposed a real bug, now fixed and covered by a test: a live collection lists each posting several times (`ALLLEDGERENTRIES.LIST`, the `LEDGERENTRIES.LIST` subset and the inventory allocation), which made 4 entries instead of 2 and would have doubled sales; the parser now merges them as a multiset union.

**Full live import, verified on 2026-11-11 against a real company (name withheld; books from 2023-04-01 to 2026-10-29):** 46 sequential read-only requests (company, masters, ledger collection, voucher census, two Trial Balances, 40 voucher months, ~746 MB in total, months of 45-72 MB) completed with TallyPrime stable; every response was captured and the import was then replayed offline, twice. Result: all 22,343 vouchers in TallyPrime's census imported (Payment 16,152, Receipt 3,043, Sales 2,092, Purchase 615, Contra 262, Journal 165, plus 9 Purchase Orders and 5 Stock Journals kept but excluded from balances), every posting voucher balanced, and the imported Trial Balance equals TallyPrime's own report to the paisa: debit = credit = <total withheld>; the opening Trial Balance (empty report, all zero) matches; all 42 ledger rows and all 21 group rows TallyPrime lists match; the `Profit & Loss A/c` row (Dr <amount withheld>) matches; all 90 non-zero ledger balances match TallyPrime's own ledger collection. A re-run changes nothing (22,343 vouchers, 1,981 ledgers unchanged). The three source XML files are unchanged.

What the full run taught (all fixed, with tests):
- A live collection lists each voucher's postings in several overlapping lists, and the complete list can show an aggregate (one ledger line) where the inventory allocation shows four item pieces. Rule now: take the first reading (complete list; party list + allocations; ...) that balances; a voucher no reading balances is rejected and reported. A first multiset-union attempt double-counted and was replaced.
- `ISDEEMEDPOSITIVE` legitimately disagrees with the amount sign (4 `Round Off` entries); the sign of `AMOUNT` is authoritative and the flag is only counted.
- Purchase Orders carry ledger entries but do not post. They net exactly to the gap that had appeared (the purchase-account total and the matching party balances). Voucher types are now classified by their parent in Tally's voucher-type master; those kinds are stored with `is_optional=1` so they stay out of balances. Only Purchase Order is verified on real data; Sales Order, Job Work orders, Memorandum, Delivery/Receipt Note, Rejections, Material In/Out, Stock Journal, Physical Stock and Attendance follow Tally's documented behaviour. The Trial Balance comparison would expose a divergence, but none of those types has postings in this company except Purchase Order.
- Response size limits were raised to 160 MB (parse) so a 72 MB month is accepted.

Still not verified or not done: bill-wise outstanding against TallyPrime's own Bills Receivable / Payable reports (not requested; see the bills paragraph below), batch/godown detail on inventory lines, stock item masters (58 placeholder items from voucher lines), cost centres, cancelled and optional vouchers (none exist in this company, so synthetic tests only), GST registration data on ledgers, and the F3 UI (still command line only). The 4 `ISDEEMEDPOSITIVE` disagreements were accepted on the sign rule and not individually reviewed. The replayed import ran into a scratch folder, not into your TallyForge data folder.

**Native `.1800` vouchers, calibrated against live TallyPrime (2026-11-11, branch `feat/native-ground-truth`):** the live capture supplied the ground truth that was missing before (all voucher types, real alter IDs, the books' real totals). `engine/native_vouchers.py` decodes every transaction record of `TranMgr.1800` in one pass (about 40 s) and `verify_native_with_capture.py` re-checks it against a capture. On the supplied company (40,348 native transaction records; 22,343 live vouchers across Payment, Receipt, Sales, Purchase, Contra, Journal, Purchase Order, Stock Journal):
- **Verified, exact:** voucher type, date and alter ID match for 22,343 of 22,343 live vouchers (matched by GUID = company GUID + master ID); the per-ledger net of every decodable voucher (22,329) equals TallyPrime's; and a native-only ledger-totals table equals the totals derived from TallyPrime's data for all 91 ledgers, total debit <total withheld> (the same figure as TallyPrime's Trial Balance). Source files were byte-identical afterwards.
- **Posting status (partly decoded):** native holds 17,986 additional records that are not live vouchers (deleted or superseded). Rule used: a record is a live voucher iff it carries the company-GUID field (3004, text), taking the highest alter ID per master. It held for all 22,343 live vouchers and failed for 2 of the 17,988 other records (masters 6518 and 6553, each with two native records); those two have no decodable postings, so they cannot change balances, but the rule is an inference, not a documented flag.
- **Decoded but not equal line by line:** for 130 Sales and Purchase invoices the native allocation list holds item-level pieces where TallyPrime shows one aggregate line; per-ledger nets still equal. These look balanced natively, so a balance check cannot reveal such a difference. Use per-ledger nets, not entry lists.
- **Not decoded:** 14 vouchers' postings (9 Purchase Orders and 5 Stock Journals, all non-posting) and the 2 false-active records above.
- **Voucher number and narration (decoded):** the number is text field 2005 (field 203 when 2005 is absent) and the narration is text field 205. The number equals TallyPrime's for all 20,281 vouchers where TallyPrime supplies one. For 2,062 Sales vouchers TallyPrime's collection and the file export return a blank number while the native file holds one, all in a single `prefix-n/yy-yy` series in date order; those cannot be checked against any source, so they are plausible, not verified. Narration equals TallyPrime's for all 22,343 after trimming; the native file keeps trailing `\r`/`\r\n` that the export trims (46 cases).
- **Not decoded or not verifiable here:** opening balances (all zero in this company, so a native decoder could not be tested against a non-zero value), cancelled and optional flags (no such voucher exists in this company), bill references, inventory quantities, GST data, and other currencies. The existing Sales-only preview in the app was not changed; the new reader has no UI.
- **Windows fix:** the native readers compared `fstat` and `stat` including inode and ctime, which differ on Windows for an untouched file, so every read failed with "changed during reading". They now compare size and modification time on Windows (`engine/native_tally.file_identity`); `test_native_reference` and `test_company_storage_api` now pass there. Three native tests that create symlinks still cannot run without the Windows symlink privilege.

- **Checked against TallyPrime's own reports** (read-only requests): outstanding bills now match its Bills Receivable (2,740 bills) and Bills Payable (696 bills) exactly, party, reference, date and amount. ## Monthly payroll

Use **F3 → Company Tools → Payroll accounts** to choose separate expense, bank/cash/payable and deduction-liability ledgers. Then open **Monthly payroll and payslips**, choose a month and posting date, and load employees. Review scheduled/paid days, overtime hours/rate, arrears, bonus and named deduction amounts for each employee. A saved attendance/payroll reference is required. Manual deduction amounts are used exactly as entered; they are not statutory rate calculations.

Regular earnings are prorated by paid days / scheduled days; overtime, arrears and bonus are added afterwards. Without saved inputs, full regular earnings and explicitly labelled legacy estimates are retained for compatibility. Older attendance rows are shown for review but are never silently applied. Preview the full month before posting. Changes to saved inputs, salary masters, accounts or the selected company invalidate that preview. Posting creates the voucher and payroll snapshots in one transaction, and month aliases such as `April 2026` and `2026-04` cannot post twice.

Finalised inputs and payroll vouchers cannot be edited/deleted/duplicated. A cancelled payroll remains visible but cannot be silently reposted; reversal/reissue still requires a reviewed correction workflow. Saved payslips survive employee/master changes and employee deletion. They can be viewed, printed with masked bank numbers or downloaded as JSON. The JSON contains payroll information, including stored account details. Data-entry/viewer roles cannot read these payroll endpoints; only administrators can change/post payroll and auditors can review it.

## Background backups

Enable the schedule in Company Tools. The application checks due backups while it is running. To continue when it is closed, configure your OS scheduler to run this command at least every five minutes, substituting real absolute paths:

```sh
/path/to/python3 /path/to/TallyForge/backup_worker.py --data-dir /path/to/CompanyData
```

Keep the scheduler's data path the same as the selected company folder. Do not schedule two overlapping workers for the same folder. Each worker checks the persisted interval, so a five-minute OS schedule does not force a backup every five minutes.

## Optional SMTP delivery

Configure `TALLY_SMTP_HOST`, `TALLY_SMTP_PORT` (465 or 587), `TALLY_SMTP_SENDER`, `TALLY_SMTP_USER`, and `TALLY_SMTP_PASSWORD` in the application environment. Secrets are never stored in company feature settings. The Send Export action asks the operator to confirm the recipient and reports SMTP acceptance, not guaranteed mailbox delivery.

## Optional AES-GCM dependency

Install `requirements-optional.txt` in the Python environment used to launch the app. No home-grown fallback is used for the new AES-GCM export. This does not enable encryption of the live SQLite file and does not make the archive compatible with native TallyVault.
